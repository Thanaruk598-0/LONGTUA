# 1. Project Overview

## 1.1 Project Identification

**ชื่อระบบ / ชื่อโครงการ:**
**LONGTUA**

**Product Descriptor:**
**Personal Adaptive Planner**

**ชื่อโครงงานภาษาไทย:**
**ระบบวางแผนส่วนบุคคลแบบปรับตัวด้วยการประมวลผลภาษาธรรมชาติและการจัดตารางภายใต้ข้อจำกัด**

**Project Title:**
**An Adaptive Personal Planning System Using Natural Language and Constraint-Based Scheduling**

LONGTUA เป็นระบบวางแผนส่วนบุคคลสำหรับผู้ใช้ทั่วไปที่ต้องการจัดการกิจกรรม งาน นัดหมาย และข้อจำกัดด้านเวลาในชีวิตประจำวัน โดยระบบออกแบบให้ผู้ใช้สามารถบอกความต้องการผ่านภาษาธรรมชาติ จากนั้นระบบจะใช้การประมวลผลภาษาธรรมชาติและปัญญาประดิษฐ์เพื่อทำความเข้าใจข้อมูลที่ผู้ใช้ระบุ แปลงเป็นข้อมูลเชิงโครงสร้าง และส่งต่อให้ Planning Engine เพื่อสร้างตารางที่สอดคล้องกับข้อจำกัดและความต้องการของผู้ใช้

ระบบไม่ได้ทำหน้าที่ตัดสินใจแทนผู้ใช้ทั้งหมด แต่ใช้แนวคิด Human-in-the-Loop โดยระบบจะเสนอแผนให้ผู้ใช้ตรวจสอบและเลือกว่าจะยืนยัน ปฏิเสธ แก้ไข หรือให้ข้อมูลเพิ่มเติม ก่อนที่แผนจะถูกนำไปใช้เป็นตารางที่ยืนยันแล้ว นอกจากนี้ เมื่อสถานการณ์เปลี่ยนแปลง เช่น เวลา กิจกรรม หรือข้อจำกัดเปลี่ยนไป ระบบสามารถนำข้อมูลใหม่มาพิจารณาและสร้างแผนใหม่ให้ผู้ใช้ตรวจสอบได้

## 1.2 Background

การจัดการเวลาในชีวิตประจำวันไม่ได้ประกอบด้วยเพียงการบันทึกว่า “ต้องทำอะไร” แต่ยังเกี่ยวข้องกับการตัดสินใจว่าแต่ละกิจกรรมควรเกิดขึ้นเมื่อใด โดยต้องพิจารณาปัจจัยหลายด้านร่วมกัน เช่น เวลาที่กำหนดไว้ ระยะเวลาที่ต้องใช้ ช่วงเวลาที่ผู้ใช้ว่าง กิจกรรมที่ไม่สามารถเลื่อนหรือทับซ้อนได้ ลำดับของกิจกรรม และความสำคัญหรือความต้องการส่วนบุคคล

เครื่องมือสำหรับจัดการตารางจำนวนมากรองรับการบันทึกกิจกรรมและกำหนดเวลาได้ดี แต่ในกระบวนการใช้งาน ผู้ใช้ยังต้องแปลงความต้องการของตนเองให้เป็นข้อมูลเชิงโครงสร้างด้วยตนเอง เช่น เลือกวันที่ เลือกเวลา ระบุระยะเวลา ตั้งการแจ้งเตือน และปรับตารางเมื่อมีการเปลี่ยนแปลง

ในชีวิตจริง ความต้องการของผู้ใช้มักไม่ได้เกิดขึ้นในรูปแบบข้อมูลที่เป็นโครงสร้างตั้งแต่ต้น ผู้ใช้อาจคิดหรือสื่อสารในลักษณะภาษาธรรมชาติ เช่น

> “พรุ่งนี้ต้องส่งรายงาน อยากทำช่วงบ่าย”

หรือ

> “พรุ่งนี้มีนัดตอนหกโมง แล้วอยากวิ่งด้วย”

ข้อความลักษณะนี้ประกอบด้วยข้อมูลหลายส่วนทั้งกิจกรรม เวลา ความต้องการ และบริบท ซึ่งระบบต้องทำความเข้าใจให้ถูกต้องก่อนจึงจะสามารถนำไปวางแผนได้

นอกจากปัญหาการป้อนข้อมูลแล้ว ตารางชีวิตยังสามารถเปลี่ยนแปลงได้ตลอดเวลา เช่น กิจกรรมเดิมถูกย้ายเวลา มีงานใหม่เข้ามา หรือมีช่วงเวลาที่ไม่สามารถใช้งานได้ การแก้ไขตารางจึงไม่ได้เป็นเพียงการเปลี่ยนเวลาของรายการหนึ่งรายการ แต่บางครั้งจำเป็นต้องพิจารณาผลกระทบต่อกิจกรรมอื่นร่วมด้วย

ด้วยเหตุนี้ LONGTUA จึงมุ่งพัฒนาระบบที่เชื่อมโยงทั้งกระบวนการตั้งแต่การทำความเข้าใจความต้องการที่ผู้ใช้ระบุด้วยภาษาธรรมชาติ การจัดตารางภายใต้ข้อจำกัด ไปจนถึงการปรับแผนเมื่อข้อมูลหรือสถานการณ์เปลี่ยนแปลง โดยยังคงให้ผู้ใช้เป็นผู้ตัดสินใจขั้นสุดท้าย

## 1.3 Preliminary User Pain Points

เพื่อทำความเข้าใจปัญหาของผู้ใช้ ทีมพัฒนาได้เก็บข้อมูลเบื้องต้นจากการสัมภาษณ์ผู้ใช้งานที่มีประสบการณ์ในการจัดการตารางชีวิตประจำวัน โดยพบประเด็นที่เกี่ยวข้องกับกระบวนการวางแผนและการปรับตารางหลายด้าน

Pain Point เหล่านี้ใช้เป็นข้อมูลตั้งต้นในการกำหนดปัญหาของโครงการและออกแบบแนวทางการแก้ปัญหา โดยไม่ได้หมายความว่าผู้ใช้ทุกกลุ่มจะมีปัญหาในระดับเดียวกัน

### 1.3.1 การสร้างตารางยังต้องกรอกข้อมูลด้วยตนเอง

ผู้ใช้ที่ให้ข้อมูลเบื้องต้นระบุว่าเครื่องมือที่ใช้อยู่ เช่น Canva, Apple Calendar, Notion, GoodNotes และ Notepad จำเป็นต้องให้ผู้ใช้กรอกหรือจัดข้อมูลด้วยตนเองก่อนที่จะได้ตารางที่พร้อมใช้งาน

กระบวนการดังกล่าวอาจมีหลายขั้นตอน เช่น

```text
คิดสิ่งที่ต้องทำ
→ เปิดเครื่องมือ
→ เลือกวัน
→ เลือกเวลา
→ กรอกชื่อกิจกรรม
→ กำหนดระยะเวลา
→ ตั้งค่าเพิ่มเติม
```

สำหรับผู้ใช้ที่ต้องการเพียงบอกสิ่งที่ต้องทำอย่างรวดเร็ว การต้องกลับมานั่งกรอกข้อมูลทุกช่องอาจเพิ่มขั้นตอนที่รู้สึกว่าไม่จำเป็น

หนึ่งในประเด็นที่ผู้ใช้สะท้อนอย่างชัดเจนคือ

> “พูดอย่างเดียวแล้วก็ขี้เกียจมานั่งกรอกตารางเอง”

ประเด็นนี้สะท้อนว่าปัญหาไม่ได้อยู่ที่ผู้ใช้ไม่มีเครื่องมือสำหรับสร้างตาราง แต่เป็นช่องว่างระหว่าง **ความตั้งใจของผู้ใช้** กับ **รูปแบบข้อมูลที่ระบบต้องการ** ซึ่งผู้ใช้ยังต้องเป็นผู้แปลงข้อมูลด้วยตนเอง

---

### 1.3.2 การเปลี่ยนแผนทำให้ต้องจัดตารางใหม่ด้วยตนเอง

อีกปัญหาที่พบคือแผนในชีวิตประจำวันไม่สามารถคงที่ได้เสมอ เช่น ผู้ใช้อาจตั้งใจอ่านหนังสือในช่วงเวลาหนึ่ง แต่ภายหลังมีนัดรับประทานอาหารหรือกิจกรรมอื่นเข้ามา ทำให้กิจกรรมเดิมต้องถูกย้ายออกจากช่วงเวลาเดิม

ตัวอย่างเช่น

```text
เดิม:
13:00–15:00 อ่านหนังสือ
15:30–17:00 ทำงาน

เกิดกิจกรรมใหม่:
14:00–15:00 ไปกินข้าว
```

เมื่อเกิดการเปลี่ยนแปลง ผู้ใช้ต้องตัดสินใจเองว่าจะ

* ย้ายกิจกรรมเดิมไปช่วงใด
* กิจกรรมใดสามารถเลื่อนได้
* จะกระทบ Deadline หรือไม่
* กิจกรรมใดควรถูกจัดก่อน
* ตารางใหม่ยังสอดคล้องกับช่วงเวลาที่ว่างหรือไม่

จึงเกิดปัญหาว่าเครื่องมือที่ใช้สำหรับ “บันทึกตาราง” ไม่ได้ช่วยจัดการ **ผลกระทบของการเปลี่ยนแปลง** ในระดับการวางแผนทั้งหมด

---

### 1.3.3 ตารางที่สร้างเองอาจไม่สะดวกต่อการตรวจสอบ

จากข้อมูลเบื้องต้น ผู้ใช้บางรายมองว่าการจัดตารางด้วยเครื่องมือที่เน้นการจัดวางด้วยตนเอง เช่น Canva สามารถปรับแต่งรูปแบบได้มาก แต่เมื่อมีรายการจำนวนมาก ตารางอาจตรวจสอบได้ยากขึ้น โดยเฉพาะเมื่อต้องการดูว่าช่วงเวลาใดมีอะไรบ้างหรือมีอะไรที่กำลังจะถึง

ประเด็นนี้เกี่ยวข้องกับการนำเสนอข้อมูลและการติดตามกิจกรรมหลังจากสร้างแผนแล้ว ไม่ใช่เพียงขั้นตอนการสร้างตาราง

---

### 1.3.4 การเตือนกิจกรรมไม่ได้แก้ปัญหาการจัดตาราง

ผู้ใช้ต้องการระบบที่ช่วยติดตามสิ่งที่วางแผนไว้ แต่การมี Reminder เพียงอย่างเดียวไม่ได้หมายความว่าปัญหาด้านการวางแผนได้รับการแก้ไข

ตัวอย่างเช่น หากกิจกรรมถูกย้ายจาก

```text
09:00 → 12:00
```

การแจ้งเตือนที่ตั้งไว้สำหรับกิจกรรมเดิมก็ควรเปลี่ยนตามตารางใหม่ด้วย

ดังนั้นระบบจึงควรมอง **Schedule เป็นข้อมูลหลัก** และมอง Notification เป็นข้อมูลที่สร้างขึ้นจาก Schedule ที่ได้รับการยืนยันแล้ว ไม่ใช่เป็นตารางอีกชุดหนึ่งที่แยกจากกัน

## 1.4 Problem Statement

จากปัญหาดังกล่าว สามารถสรุปปัญหาหลักของโครงการได้เป็น 3 ประเด็น

### Problem 1: Input Burden

ผู้ใช้ต้องแปลงความต้องการหรือสิ่งที่ต้องทำให้เป็นข้อมูลที่มีโครงสร้างด้วยตนเองก่อนจึงจะสร้างตารางได้ ส่งผลให้กระบวนการบันทึกกิจกรรมมีขั้นตอนมากกว่าการระบุความต้องการตามธรรมชาติของผู้ใช้

### Problem 2: Planning Burden

เมื่อมีกิจกรรมหลายรายการและมีข้อจำกัดด้านเวลา ผู้ใช้ต้องพิจารณาด้วยตนเองว่าควรจัดกิจกรรมแต่ละรายการในช่วงเวลาใดจึงจะไม่เกิดความขัดแย้งและยังสอดคล้องกับความต้องการ

### Problem 3: Replanning Burden

เมื่อสถานการณ์เปลี่ยน ผู้ใช้ต้องพิจารณาผลกระทบและจัดตารางใหม่ด้วยตนเอง ซึ่งยิ่งมีจำนวนกิจกรรมและข้อจำกัดมาก กระบวนการดังกล่าวยิ่งมีความซับซ้อน

จากทั้งสามประเด็น โครงการจึงมุ่งแก้ปัญหาที่เกิดขึ้นระหว่าง

> **การบอกความต้องการ → การสร้างแผน → การปรับแผนเมื่อสถานการณ์เปลี่ยน**

แทนที่จะมุ่งเป็นเพียงระบบสำหรับบันทึก Calendar หรือ To-do List

## 1.5 Proposed Solution

LONGTUA เสนอแนวทางในการลดภาระของผู้ใช้โดยแบ่งกระบวนการวางแผนออกเป็นส่วนที่แต่ละองค์ประกอบของระบบรับผิดชอบอย่างชัดเจน

```text
User Intent
    ↓
Natural Language Input
    ↓
AI / NLP
    ↓
Structured Planning Information
    ↓
Validation / Normalization
    ↓
Planning Representation
    ↓
Planning Engine
    ↓
Candidate Plan(s)
    ↓
Proposal
    ↓
User Review
    ├── Confirm
    ├── Reject
    ├── Manual Edit
    └── Feedback
              ↓
          Replanning
              ↓
        New Proposal
```

AI/NLP ทำหน้าที่ทำความเข้าใจข้อความของผู้ใช้ เช่น กิจกรรม เวลา ระยะเวลา วันที่ ความสัมพันธ์ของกิจกรรม และข้อมูลที่จำเป็นต่อการวางแผน

หลังจากนั้น Planning Engine จะนำข้อมูลที่ผ่านการตรวจสอบเข้าสู่กระบวนการจัดตาราง โดยพิจารณา Hard Constraints และ Preferences เพื่อสร้างแผนที่เป็นไปได้

ผลลัพธ์จะถูกนำเสนอให้ผู้ใช้ตรวจสอบก่อนเสมอ ผู้ใช้สามารถยอมรับ ปฏิเสธ แก้ไข หรือให้ข้อมูลเพิ่มเติมได้ ระบบจึงไม่เปลี่ยน Confirmed Schedule โดยอัตโนมัติ

เมื่อมีข้อมูลใหม่หรือสถานการณ์เปลี่ยน ระบบสามารถนำข้อมูลดังกล่าวเข้าสู่กระบวนการ Replanning เพื่อสร้าง Proposal ใหม่ที่สะท้อนบริบทล่าสุด

## 1.6 Core Concept

แนวคิดหลักของ LONGTUA คือ

> **“ให้ผู้ใช้บอกสิ่งที่ต้องการในรูปแบบที่เป็นธรรมชาติ แล้วช่วยจัดวางกิจกรรมให้อยู่ในแผนที่สอดคล้องกับข้อจำกัดและสามารถปรับใหม่ได้เมื่อสถานการณ์เปลี่ยน”**

ระบบประกอบด้วยแนวคิดสำคัญ 4 ส่วน

### 1. Natural Language Interaction

ผู้ใช้สามารถเริ่มต้นการวางแผนจากข้อความภาษาธรรมชาติ แทนการกรอกข้อมูลเชิงโครงสร้างทุกส่วนด้วยตนเอง

### 2. Constraint-Based Planning

ระบบใช้ Planning Engine เพื่อจัดกิจกรรมภายใต้ข้อจำกัด เช่น เวลาที่กำหนด ระยะเวลา Deadline Availability Unavailability และความสัมพันธ์ระหว่างกิจกรรม

### 3. Adaptive Replanning

เมื่อตารางเดิมได้รับผลกระทบจากข้อมูลใหม่ ระบบสามารถสร้างแผนใหม่ภายใต้บริบทที่เปลี่ยนไป โดยคำนึงถึงทั้ง Requirement ใหม่และความเสถียรของตารางเดิม

### 4. Human-in-the-Loop

ระบบเสนอแผน แต่ผู้ใช้เป็นผู้ตัดสินใจขั้นสุดท้าย โดยสามารถ Confirm, Reject, Edit หรือให้ Feedback ได้

ดังนั้น LONGTUA จึงไม่ใช่ระบบที่มุ่ง “จัดชีวิตแทนผู้ใช้” แต่เป็นระบบที่ช่วยลดภาระในการตีความและจัดตาราง ขณะที่ยังคงให้ผู้ใช้ควบคุมผลลัพธ์สุดท้าย

---

## 1.7 Project Objectives

โครงการมีวัตถุประสงค์หลักดังต่อไปนี้

### Objective 1

พัฒนาระบบที่สามารถแปลงข้อความภาษาธรรมชาติของผู้ใช้ให้เป็นข้อมูลเชิงโครงสร้างที่เหมาะสมสำหรับการวางแผน

### Objective 2

พัฒนากระบวนการจัดตารางที่สามารถพิจารณา Hard Constraints และ Preferences ของผู้ใช้เพื่อสร้างตารางที่เป็นไปได้และสอดคล้องกับความต้องการ

### Objective 3

พัฒนากระบวนการ Replanning ที่สามารถสร้างแผนใหม่เมื่อข้อมูลหรือสถานการณ์ของผู้ใช้เปลี่ยนแปลง โดยลดการเปลี่ยนแปลงของกิจกรรมที่ไม่จำเป็น

### Objective 4

พัฒนากระบวนการ Human-in-the-Loop ที่ให้ผู้ใช้สามารถตรวจสอบ ยืนยัน ปฏิเสธ แก้ไข และให้ Feedback ต่อแผนที่ระบบสร้างขึ้น

### Objective 5

ประเมินประสิทธิภาพของระบบในด้านการทำความเข้าใจข้อมูล การจัดตาราง การปรับแผน และการโต้ตอบกับผู้ใช้ด้วยตัวชี้วัดที่เหมาะสมกับแต่ละกระบวนการ

---

## 1.8 Target Users

LONGTUA ออกแบบสำหรับ **ผู้ใช้ทั่วไปที่ต้องจัดการกิจกรรมหลายประเภทในชีวิตประจำวัน** โดยไม่จำกัดเฉพาะนักเรียนหรือนักศึกษา

ตัวอย่างผู้ใช้งาน ได้แก่

* ผู้ที่ต้องจัดการงานส่วนตัวและงานประจำวันหลายรายการ
* ผู้ที่มีนัดหมายหรือกิจกรรมตามเวลาที่กำหนด
* ผู้ที่ต้องจัดการกิจกรรมที่มี Deadline
* ผู้ที่มีช่วงเวลาว่างและไม่ว่างแตกต่างกัน
* ผู้ที่ต้องเปลี่ยนตารางบ่อยเนื่องจากสถานการณ์ในแต่ละวัน

ระบบให้ความสำคัญกับผู้ใช้ที่ต้องการ **ลดขั้นตอนการสร้างตารางและลดภาระในการจัดตารางใหม่เมื่อแผนเปลี่ยน**

## 1.9 Expected Benefits

ผลประโยชน์ที่คาดว่าจะได้รับจากระบบแบ่งออกเป็น 3 ด้าน

### ด้านผู้ใช้

ลดภาระในการเปลี่ยนความตั้งใจให้เป็นข้อมูลตาราง ลดการจัดกิจกรรมด้วยตนเอง และช่วยให้ผู้ใช้สามารถตรวจสอบแผนที่ระบบสร้างขึ้นก่อนนำไปใช้งานจริง

### ด้านการวางแผน

ช่วยพิจารณาความสัมพันธ์ระหว่างกิจกรรม เวลา และข้อจำกัดหลายรายการพร้อมกัน ทำให้การจัดตารางไม่ขึ้นอยู่กับการตัดสินใจของผู้ใช้เพียงอย่างเดียวในทุกขั้นตอน

### ด้านการปรับตัว

เมื่อสถานการณ์เปลี่ยน ระบบสามารถนำข้อมูลใหม่มาสร้าง Proposal ใหม่แทนการให้ผู้ใช้จัดตารางทั้งหมดด้วยตนเองอีกครั้ง

## 1.11 System Boundaries

เพื่อป้องกันความคลาดเคลื่อนด้านขอบเขต ระบบกำหนดบทบาทของแต่ละส่วนไว้อย่างชัดเจน

```text
Mobile Application
    = User Interaction

AI / NLP
    = Understanding

Validation / Normalization
    = ตรวจสอบและทำข้อมูลให้พร้อมใช้งาน

Planning Engine
    = Scheduling / Optimization

Schedule Management
    = จัดการ Confirmed Schedule และ Version

Notification
    = แจ้งเตือนจาก Confirmed Schedule

User
    = Final Decision Maker
```

กฎสำคัญคือ

> AI ไม่ทำหน้าที่แทน Planning Engine
> Planning Engine ไม่ทำหน้าที่ตีความภาษาธรรมชาติ
> ระบบไม่เปลี่ยน Confirmed Schedule โดยปราศจากการยืนยันของผู้ใช้

## 1.12 Design Philosophy

LONGTUA ใช้หลักการออกแบบว่า

> **AI proposes, Planner computes, User decides.**

กล่าวคือ AI มีหน้าที่ทำความเข้าใจความต้องการของผู้ใช้ Planning Engine มีหน้าที่คำนวณและจัดตารางภายใต้ข้อจำกัด และผู้ใช้เป็นผู้ตัดสินใจว่าจะยอมรับผลลัพธ์หรือไม่

หลักการนี้ถูกใช้เป็นพื้นฐานร่วมกันในทุกส่วนของระบบ ตั้งแต่การออกแบบข้อมูล การทำงานของ AI/NLP การจัดตาราง การ Replanning การจัดการ Proposal จนถึงการแจ้งเตือน

---

## 1.13 Project Positioning

LONGTUA ไม่ได้มุ่งนำเสนอเพียง Calendar หรือ To-do List รูปแบบใหม่ แต่เป็นระบบที่พยายามลดภาระของผู้ใช้ในกระบวนการวางแผนทั้งหมด โดยเชื่อมต่อ 3 ขั้นตอนสำคัญเข้าด้วยกัน ได้แก่

```text
1. Understand
   เข้าใจว่าผู้ใช้ต้องการอะไร

2. Plan
   จัดวางกิจกรรมภายใต้ข้อจำกัด

3. Adapt
   ปรับแผนเมื่อสถานการณ์เปลี่ยน
```

จุดสำคัญของระบบจึงอยู่ที่การบูรณาการ **Natural Language Understanding, Constraint-Based Scheduling, Adaptive Replanning และ Human-in-the-Loop** เข้าด้วยกันภายในกระบวนการวางแผนส่วนบุคคลเดียวกัน

## 1.14 Project Summary

LONGTUA — Personal Adaptive Planner เป็นระบบวางแผนส่วนบุคคลที่ออกแบบมาเพื่อช่วยลดภาระของผู้ใช้ในการเปลี่ยนความต้องการให้เป็นตารางและในการจัดตารางใหม่เมื่อสถานการณ์เปลี่ยน โดยใช้ AI/NLP เพื่อทำความเข้าใจข้อความภาษาธรรมชาติ และใช้ Constraint-Based Planning เพื่อสร้างตารางภายใต้ข้อจำกัดและความต้องการของผู้ใช้

ระบบนำเสนอผลลัพธ์ในรูปแบบ Proposal เพื่อให้ผู้ใช้ตรวจสอบและตัดสินใจด้วยตนเองก่อนสร้าง Confirmed Schedule และเมื่อมีข้อมูลหรือสถานการณ์ใหม่ ระบบสามารถดำเนินการ Replanning เพื่อสร้างข้อเสนอใหม่ โดยยังคงรักษาหลักการสำคัญว่าผู้ใช้เป็นผู้ควบคุมและตัดสินใจผลลัพธ์สุดท้าย

ดังนั้นแนวคิดหลักของ LONGTUA สามารถสรุปได้ว่า

> **บอกสิ่งที่ต้องการ → ให้ระบบช่วยจัดแผน → ผู้ใช้ตรวจสอบและตัดสินใจ → เมื่อสถานการณ์เปลี่ยน ระบบช่วยปรับแผนใหม่**
